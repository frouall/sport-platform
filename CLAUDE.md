# Проект: интеллектуальная веб-платформа для любительского спорта

Тема: «Разработка интеллектуальной веб-платформы координации любительской спортивной деятельности, управления игровыми мероприятиями и формирования сообществ участников».

## 1. Цель и контекст
Веб-приложение, где любители спорта находят партнёров и игры рядом с собой, организаторы создают и ведут игровые мероприятия, а участники объединяются в сообщества. «Интеллектуальность» — это подбор подходящих игр и людей, балансировка составов, оценка риска неявки и (опционально) ИИ-помощник.

Проект учебный/дипломный, ведёт один разработчик. Основной язык интерфейса и документации — русский (с возможностью добавить казахский и английский позже). Код, имена переменных и коммиты — на английском.

## 2. Жёсткое ограничение: всё бесплатно
Нельзя предлагать и использовать ничего, что требует оплаты или банковской карты. Перед выбором любого сервиса сверяйся с актуальными лимитами бесплатного тарифа и пиши их в docs/stack.md.

Стек по умолчанию:
- Frontend: Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui
- Backend/БД: Supabase Free (PostgreSQL, Auth, Row Level Security, Realtime, Storage)
- Карты: Leaflet + OpenStreetMap (без ключей API)
- Хостинг: Vercel Hobby или Cloudflare Pages
- ИИ: основной слой — собственные алгоритмы (скоринг, правила, простая статистика) без внешних API. Опционально ИИ-помощник через бесплатный тариф Gemini API или Groq, с обязательным fallback без LLM
- Тесты: Vitest + Playwright; CI: GitHub Actions
- Репозиторий: GitHub (публичный или приватный бесплатный)

Если нужно отклониться от стека, сначала объясни причину и предложи бесплатную альтернативу.

## 3. Роли пользователей
- Игрок: профиль, виды спорта и уровень, поиск игр, запись, лист ожидания, оценки, сообщества
- Организатор: создание и ведение мероприятий, отметка посещаемости, управление сообществом
- Администратор: модерация пользователей, мероприятий и жалоб, справочники, статистика

## 4. Функциональные требования

MVP (обязательно):
1. Регистрация и вход (email + пароль, Google OAuth), профиль, виды спорта, уровень 1–5, район/город
2. Каталог площадок (название, адрес, координаты, тип покрытия, вид спорта)
3. Создание мероприятия: вид спорта, площадка, дата и время, лимит участников, минимальный уровень, формат (дружеская/тренировка/турнир), цена (информационно)
4. Поиск и фильтры по спорту, дате, уровню, району; карта мероприятий
5. Запись, отмена, автоматический лист ожидания с автопродвижением очереди
6. Сообщества: создание, вступление (открытое/по заявке), лента, участники, роли внутри сообщества
7. Чат мероприятия и сообщества в реальном времени
8. Уведомления (внутри приложения, затем email через бесплатный SMTP)
9. Рейтинг и репутация: оценки после игры, процент посещаемости, значки
10. Админ-панель

Интеллектуальный модуль:
- Рекомендации мероприятий: скоринг по спорту, уровню, расстоянию, времени, истории и интересам; объяснение «почему рекомендовано»
- Балансировка команд: автоматическое разбиение участников на равные по силе составы
- Оценка риска неявки: простая модель по истории посещаемости, времени и дню недели; помощь организатору с овербукингом
- Рекомендации сообществ и «похожих игроков»
- Опционально: ИИ-помощник («создай игру в футбол на завтра вечером на 10 человек») с fallback на форму

Не входит в MVP: платежи, мобильное приложение, видео, турнирные сетки на много этапов.

## 5. Нефункциональные требования
- Безопасность: RLS на всех таблицах, проверка прав на сервере, валидация входных данных (zod), защита от XSS/CSRF, секреты только в переменных окружения, никаких ключей в репозитории
- Приватность: точная геолокация пользователя не хранится без согласия; можно удалить аккаунт и данные
- Производительность: LCP < 2.5 с на среднем мобильном устройстве, индексы на частые запросы
- Доступность и адаптивность: mobile-first, контраст и подписи по WCAG AA
- Качество: TypeScript strict, ESLint, покрытие тестами ключевой бизнес-логики

## 6. Порядок работы (этапы)
Двигайся строго по этапам. В конце каждого этапа остановись, коротко отчитайся и дождись подтверждения пользователя.

- Этап 0. Подготовка: репозиторий, структура папок, окружение, подключение Supabase, CI
- Этап 1. Анализ: роли, пользовательские истории, MVP-границы, риски (docs/requirements.md)
- Этап 2. Проектирование: ER-диаграмма, схема БД, политики RLS, API/маршруты, макеты экранов (docs/architecture.md, db/schema.sql)
- Этап 3. Ядро: авторизация, профили, площадки, мероприятия, запись и лист ожидания
- Этап 4. Сообщества и реальное время: сообщества, чаты, уведомления
- Этап 5. Интеллект: рекомендации, балансировка, риск неявки, опциональный ИИ-помощник
- Этап 6. Качество: тесты, ревью безопасности, оптимизация, доступность
- Этап 7. Релиз и документация: деплой, демо-данные, руководство, пояснительная записка, презентация

## 7. Команда агентов
Файлы агентов лежат в .claude/agents/. Ты — главный координатор и сам решаешь, кого вызвать.

| Агент | Когда вызывать |
|---|---|
| product-analyst | Требования, истории, приоритеты, границы MVP |
| architect | Структура проекта, схема БД, RLS, договорённости между модулями |
| backend-dev | SQL-миграции, серверная логика, Supabase, Realtime |
| frontend-dev | Страницы, компоненты, формы, карта, адаптивность |
| ai-engineer | Рекомендации, балансировка, риск неявки, ИИ-помощник |
| qa-security | Тесты, поиск багов, проверка безопасности и RLS |
| docs-writer | Документация, диаграммы, пояснительная записка, презентация |

Правила работы с агентами:
- Независимые задачи запускай параллельно (например, backend-dev и frontend-dev над разными модулями после согласованной схемы БД)
- Каждому агенту ставь конкретную задачу, входные файлы и ожидаемый результат
- После крупных изменений обязательно вызывай qa-security
- architect утверждает любые изменения схемы БД до того, как backend-dev их применит

## 8. Правила для тебя
1. Сначала план, потом код. Для каждого этапа покажи короткий план и жди «ок»
2. Объясняй просто: пользователь учится, поэтому добавляй короткое «что и зачем сделано»
3. Маленькие шаги и частые коммиты (Conventional Commits)
4. Не выдумывай: если не уверен в API или лимите бесплатного тарифа, проверь по документации
5. Не добавляй платные зависимости, не проси карту, не запускай деструктивных команд без подтверждения
6. Если требование неясно, задай один конкретный вопрос
7. Веди docs/progress.md: что сделано, что дальше, открытые вопросы
8. Любое готовое решение сопровождай способом проверки (команда, тест или шаги в браузере)

## 9. Структура репозитория
```
/src            приложение Next.js (app, components, lib)
/src/lib/ai     алгоритмы рекомендаций, балансировки, риска

```

## 10. Критерии готовности (Definition of Done)
Функция считается готовой, когда: работает по сценарию, есть валидация и проверка прав, есть тест на ключевую логику, нет ошибок линтера и типов, обновлена документация и progress.md.

## 11. Первое действие
Прочитай этот файл целиком, предложи краткий план Этапа 0 и Этапа 1, назови, какие агенты понадобятся, и спроси только то, без чего нельзя начать (например, город запуска и виды спорта для старта).
